## 1. The three APIs, measured rather than documented

020 §4 named `Blob.stream()`, `crypto.subtle.digest` and `CompressionStream` as the
upload page's platform requirements and closed by saying browser support for all three
"is taken from documentation rather than measured here; only Chromium was available".
It is now measured, and in a way a `typeof` check would not have settled: **each API is
exercised and its output checked**, because an API that is present and wrong is worse
than one that is absent — the digest is 011's duplicate check and the gzip is what R2
receives.

| Check | WebKit 26.5 | Gecko 153 | Blink 151 |
|---|---|---|---|
| `Blob.prototype.stream` is a function, and a read returns the bytes | ok | ok | ok |
| `new CompressionStream('gzip')` constructs, and the output starts `1f 8b` — gzip, not bare deflate | ok | ok | ok |
| `crypto.subtle.digest('SHA-256', …)` returns `ba7816bf…20015ad` for `"abc"` | ok | ok | ok |
| `isSecureContext` | true | true | true |
| `crossOriginIsolated` | true | true | true |

**Nothing is missing and nothing is subtly wrong.** 020's documentary claim holds in the
two engines it could not reach.

Two things fall out that are worth keeping.

**The gzip magic check earned its place.** `CompressionStream` takes `'gzip'`,
`'deflate'` and `'deflate-raw'`, and the three differ only in a header. An engine that
accepted `'gzip'` and emitted raw deflate would pass a `typeof` probe, pass a
round-trip-in-the-same-engine probe, and produce an object R2 stores happily and ingest
cannot read. All three engines emit real gzip.

**The origin the page is served from removes one of the three requirements, silently.**
`crypto.subtle` is gated on a secure context; `Blob.stream()` and `CompressionStream` are
not. So an insecure origin does not fail loudly — it deletes exactly one requirement, the
content hash, which is 011's dedup key. Measured three ways in each engine
(`origin-check.mjs`), and all three engines agree exactly:

| Origin | `isSecureContext` | `crypto.subtle` | `CompressionStream` | `Blob.stream()` |
|---|---|---|---|---|
| `http://localhost:<port>/` | true | **present** | present | present |
| `file:///…/bench.html` | true | **present** | present | present |
| **`http://172.20.57.251:<port>/`** (LAN address) | **false** | **absent** | present | present |

This is the trap waiting for the iOS test this ticket cannot run. The natural way to get
a harness onto a borrowed iPhone is to serve it from the laptop and open
`http://192.168.x.x:8137` on the phone — and on that origin `crypto.subtle` is gone in
**every** engine, which reads as *"Safari has no WebCrypto"* and produces a false
negative on the exact question the test was for. Whoever runs it must use `https://`,
a tunnel, or the device's own `localhost`. `file://` would work but cannot carry the
COOP/COEP headers and cannot be got onto a phone conveniently.

## 2. It completes, and it is not slower in WebKit

Five repeats per engine, each in a **fresh browser process**. `hash` is
`crypto.subtle.digest` over `file.arrayBuffer()`; `scan+gzip` is the tee'd single pass.

| Engine | Completes | Wall ms — min / median / max | hash ms | scan+gzip ms |
|---|---|---|---|---|
| **WebKit 26.5** | **5/5** | 512 / **535** / 614 | 80 | 455 |
| **Gecko 153** | **5/5** | 661 / **678** / 686 | 107 | 568 |
| Blink 151 | 5/5 | 630 / **634** / 647 | 59 | 575 |
| *020, Chrome for Testing 149* | *1* | *— / 661 / —* | *155* | *506* |

**WebKit is the fastest of the three on this workload** — 21% below Gecko and 16% below
Blink — and every engine is inside 0.7 seconds for a file at the byte cap. The
ticket asked whether the scan completes; it completes with the same margin everywhere.

The Blink control lands within 4% of 020's figure (634 ms against 661 ms) across two
Chrome majors (a `chrome-headless-shell` 151 here against 020's Chrome for Testing 149),
a rebuilt harness and a regenerated fixture — which is the check that this harness is
measuring the same thing 020 measured. The internal split moved: this harness's hash is
2.6× faster and its scan+gzip 14% slower. That is two engine majors and a differently
structured tokenizer, not a disagreement about the total.

### Scale

One run each. Linear in file size in all three engines, with no knee.

| Fixture | Raw MB | WebKit ms | Gecko ms | Blink ms |
|---|---|---|---|---|
| `perf-2k` | 3.29 | 42 | 51 | 47 |
| `perf-20k` | 30.66 | 337 | 426 | 362 |
| `perf-20k-dense` | 35.01 | 429 | 590 | 419 |
| **`cap-33k`** | **50.55** | **519** | **794** | **578** |

`perf-20k-dense` is 14% more bytes than `perf-20k` and 52% more records, and it costs
27% more in WebKit and 38% more in Gecko — so the cost tracks records more than bytes,
which is what a line-oriented tokenizer should do.

## 3. Memory, and what the number is actually made of

**No engine but Blink has an in-page memory instrument.** `performance.memory` is absent
in WebKit and Gecko, as the ticket assumed. `performance.measureUserAgentSpecificMemory()`
is absent in both as well, and in the Blink build used here it is *present but throws*
`SecurityError: … is not available` despite `crossOriginIsolated === true` — so the
retained-memory reading 020 took from it is not reproduced here in any engine.

What every engine does have is the OS. The figure below is **`VmHWM` after the run minus
`VmHWM` once the page had loaded and settled**, on the same processes in the same browser
instance. It is a *lower bound* — a run that peaks below its own startup high-water mark
reads as zero — and it is the only cross-engine reading available.

| Engine | Peak growth, median of 5 | range |
|---|---|---|
| **WebKit 26.5** | **360 MiB** | 356–416 |
| **Gecko 153** | **190 MiB** | 189–200 |
| Blink 151 | 234 MiB | 233–240 |

Blink additionally reports **139 MiB median peak JS heap** (84.9–193.2 across the five
runs, with `--enable-precise-memory-info`), against 020's 73.8 MiB for the same variant
on Chrome 149. The gap is mostly sampling: this harness polls `performance.memory` every
10 ms through the run, and the peak of a sampled series moves with the sampling.

### Most of that number is the harness fetching the file, and WebKit's share is the interesting one

Same file, the client step taken apart, one run each:

| Stage | WebKit MiB | Gecko MiB | Blink MiB |
|---|---|---|---|
| **fetch the file and stop** | **269.6** | 149.5 | **49.7** |
| scan only, no hash, no gzip | 420.9 | 149.9 | 148.8 |
| scan + hash | 423.7 | 149.3 | 214.1 |
| scan + gzip | 380.3 | 148.7 | 188.1 |
| **full client step** | **368.7** | 190.0 | 240.2 |

Two things to read out of this, and one not to.

**Blink's fetch costs 49.7 MiB for a 48.2 MiB file — 1.03×, exactly the bytes. WebKit's
costs 269.6 MiB, 5.6×** in the web process, with a further 183.2 MiB of growth in a
second WebKit process alongside it. Gecko's is 149.5 MiB, 3.1×. That cost is **the harness, not the
scan**: `fetch()` → `Response.blob()` is how the bench gets a `File`, and the real
upload page gets one from `<input type="file">`, which is disk-backed and costs
approximately nothing. It is recorded because it bounds everything else in the column —
WebKit's full-step figure of 368.7 MiB has 269.6 MiB of transport underneath it, so the
scan's own share is ~99 MiB, against Blink's ~190 MiB over a much cheaper fetch.

**It is also a live finding for anywhere the product fetches a `.xer` into a Blob.**
Nothing in 011's flow does — upload is a file picker — but a "fork this and re-upload"
affordance or a client-side re-scan of a published file would, and in WebKit that is
5.6× the file before any work begins.

**What not to read out of it: the non-monotonic rows.** WebKit's `scan-only` (420.9)
above its `full` (368.7), and Gecko's four rows pinned within 1 MiB of its fetch cost,
are the instrument's floor showing through — one run each, and a lower bound that
saturates once the fetch has already set the high-water mark. The five-repeat table above
is the number to quote; this one is for the shape.

## 4. The scan gives the same answers in all three engines, and they are the right answers

The thing a "does it complete" test cannot catch is an engine that completes and is
wrong. Two checks, both over the whole committed 27-file corpus, run inside each engine:

```
27/27 corpus fixtures produce a byte-identical ScanResult in webkit, firefox, chromium
27/27 corpus fixtures scan correctly against 012's goldens
```

Byte-identical means the serialised `ScanResult` — every table row count, every mix,
every capped list, every date bound — is the same string in all three engines. Nothing
differs, including the things most likely to: CP1252 decoding of the `0x80-0x9F` block
(`TextDecoder('windows-1252')` is present in all three and was verified to map `0x97`
to an em dash rather than to U+0097 before being trusted), the continuation-line rule,
and the per-file `%F` name→index mapping.

Including 011's discriminator, which survives the move to two more engines intact:

| Fixture | `distinct_task_proj_id` | `PROJECT` rows | Verdict |
|---|---|---|---|
| `multiproj-two-proj-id` | **2** | 2 | reject — multi-project |
| `multiproj-baseline-rows` | **1** | **3** | accept |

And 040's readability guard, which is the newest thing in the `ScanResult` and had never
been run outside Chromium: `enc-zeroed-file` and `enc-truncated-export` both report
`reaches_end_marker: false` with the golden's exact `nul_byte_count`, in all three
engines.

**The content hash agrees across engines and with Node.** `cap-33k`'s SHA-256 is
`c4dbce13…c708012e` from `crypto.subtle` in WebKit, in Gecko, in Blink, and from Node's
`crypto` over the same file. 020 cross-checked three implementations in one engine; this
is one implementation across three engines and a fourth runtime.

## 5. `CompressionStream` output is engine-dependent, and in Gecko not even run-stable

Not a question the ticket asked, and the sharpest thing the run turned up.

| Engine | `cap-33k` gzipped, 5 runs | Ratio |
|---|---|---|
| WebKit 26.5 | 7,383,836 ×5 | 6.85 : 1 |
| **Gecko 153** | **7,192,108 ×4, 7,192,343 ×1** | 7.03 : 1 |
| Blink 151 | 7,155,680 ×5 | 7.06 : 1 |
| *Node 24.18 `zlib.gzipSync`, default level* | *7,155,680* | *7.06 : 1* |

Same bytes in, three different lengths out — a spread of **228 KB, 3.2%** — and Blink's
output is byte-for-byte the length Node's default `gzipSync` produces. **Gecko's is not
even deterministic across runs of the same engine on the same file**: one of five runs
came out 235 bytes longer, which is stream chunk boundaries landing differently against
deflate's block flushing under different scheduling.

This **confirms 020's hardening note and upgrades it from prudent to required**. 020 said
presign must issue an *exact* content-length "because the client has already produced the
compressed blob… R2 rejects anything else, so the cap does not rest on client honesty".
The measurement adds a second, independent reason: **the compressed length is not a
function of the file.** It cannot be predicted server-side, it cannot be predicted from
another engine, and in Gecko it cannot be predicted from the same engine's previous
answer. Anything that computes an expected gzip length anywhere but from the blob in
hand is wrong.

It also puts one condition on a retry that nothing has stated: **a retry must PUT the
same blob, or fetch a new presigned URL.** Re-gzipping the file to retry a failed upload
can produce a different length in Gecko, and the presigned URL's exact content-length
would then reject it. 020 already retains the blob for the PUT, so the code as decided is
correct — but the correctness depends on retaining it, and until now that looked like an
optimisation.

## 6. 020's device proxy does not port, and saying so is most of what this section is for

020 §3's evidence rests on a **capped V8 old space** as a stand-in for a constrained
device: `--js-flags=--max-old-space-size=N`, on the grounds that a renderer exceeding it
is killed with nothing catchable, which is the failure *shape* mobile Safari produces.
The obvious move here was to do the same in the other two engines.

It was done, with each engine's nearest equivalent, and then — before reading any of it —
the knob itself was tested: **set a 16 MiB ceiling, then allocate 512 MiB of live strings
in the page.** An engine enforcing the ceiling must throw or die.

| Engine | Knob | Allocating 512 MiB under a nominal 16 MiB ceiling |
|---|---|---|
| Blink | `--js-flags=--max-old-space-size=16` | **died, uncatchably** — the knob bites |
| Gecko | `javascript.options.mem.max = 16384` | **survived** — the knob is a **no-op** |
| WebKit | `JSC_gcMaxHeapSize=16777216` | **survived** — the knob is a **no-op** |

So the constrained matrix reads as follows, and two thirds of it is void:

| Engine | Workload | 512 | 256 | 128 | 64 | 32 | 16 | 8 |
|---|---|---|---|---|---|---|---|---|
| **Blink** | full client step | ok | ok | ok | ok | ok | **ok** | **died** |
| **Blink** | full parse (control) | ok | **died** | died | died | died | died | died |
| WebKit | either | *void* | *void* | *void* | *void* | *void* | *void* | *void* |
| Gecko | either | *void* | *void* | *void* | *void* | *void* | *void* | *void* |

**The Blink rows reproduce 020 §3 and extend it.** The scan survives a **16 MiB** old
space on a 50.5 MB file and dies at 8 MiB; the retaining full parse of the same file
survives 512 MiB and **dies at 256**. 020 measured the parse dying at 64 MiB on the
30.7 MB `perf-20k`; on the 50.5 MB file it needs somewhere between 256 and 512. The gap
between the two drivers is at least **16×** and the scan is on the right side of it.
Both drivers run through the *same tokenizer* in this harness (020 §6's seam, built that
way on purpose), so the 16× is the collection strategy and nothing else.

**The WebKit and Gecko rows say nothing at all.** "Survives an 8 MiB heap" and "the flag
was ignored" are indistinguishable from the scan's own output, and the knob check says it
is the second. There is no way to manufacture the uncatchable-death condition in
Playwright's WebKit or Gecko builds from the outside, so the part of 020's argument that
runs *"the remedy wins because it never produces the condition"* is still evidenced in
Blink alone.

What replaces it, for those two engines, is weaker and worth stating as weaker: the scan
completes, it is linear, it costs 190–360 MiB of process growth of which most is the
harness's own transport, and it produces identical output to the engine where the proxy
does work.

## 7. What could not be measured, stated plainly

- **iOS Safari: not measured, and not measurable on this machine at any effort.** The
  dev has no iOS device and no Mac. iOS enforces a ceiling on a tab's *total process*
  memory, in the OS, and kills the tab; desktop WebKit has no such ceiling, so no run
  here produces the condition. **No figure in this document is an iOS figure.**
- **Playwright's WebKit is not the WebKit Apple ships.** It is the same engine source
  built for Linux as WPE, at a revision whose `Version/26.5` corresponds to a shipping
  Safari, and it is a far better witness than documentation — but it is not
  byte-identical to Safari, it has no Apple-platform integration, and its
  `CompressionStream` and `crypto.subtle` are backed by the Linux port's libraries.
  Every §1 result should be read as "WebKit does this", not "Safari 26.5 on an iPhone
  does this".
- **Desktop Safari: not measured either.** The ticket asked for it and it needs a Mac.
  It is the *less* interesting of the two — a desktop tab has memory — and it is the one
  a borrowed machine could settle in ten minutes.
- **No real device of any kind.** Every engine here ran on a 16-vCPU / 24 GB desktop.
  The wall times are desktop wall times; a phone's are slower by some factor nothing
  here measures.
- **Retained memory after settling.** 020's third reading came from
  `performance.measureUserAgentSpecificMemory()`, which is absent in WebKit and Gecko and
  throws in this Blink build. 020's "3 MB retained, flat across a 200× range of file
  size" is **not reproduced in any engine here** and is not contradicted either.

| Instrument | Cost | What it settles |

## Appendix: getting WebKit to run on a headless Linux box without root

Recorded because it is the whole reason 020 could not do this, and it costs about ten
minutes once known. On this machine `npx playwright install --with-deps webkit firefox`
**fails**: the download succeeds, then the dependency step tries to `sudo apt-get install`
and dies with `sudo: A terminal is required to authenticate`. Without `--with-deps` the
browsers download and only the host-library validation fails.

Firefox then runs as-is. WebKit does not — Playwright bundles `libsoup` and
`libbacktrace` in `minibrowser-wpe/sys/lib` and expects the rest from the system:

```
libenchant-2 · libflite (14 objects) · libgstreamer-plugins-{base,bad,extra} ·
libgstreamer-gl · libgstcodecparsers · liborc · libgudev · libharfbuzz-icu ·
libhyphen · libopus · libwayland-server · libxslt · libGLESv2
```

All of them are ordinary Ubuntu packages, and `apt-get download` needs no root:

```bash
mkdir -p deps/debs deps/root && cd deps/debs
apt-get download libenchant-2-2 libflite1 libgstreamer-plugins-base1.0-0 \
  libgstreamer-plugins-bad1.0-0 libgstreamer-plugins-extra1.0-0 libgstreamer-gl1.0-0 \
  liborc-0.4-0t64 libgudev-1.0-0 libharfbuzz-icu0 libhyphen0 libopus0 \
  libwayland-server0 libxslt1.1 libgles2
cd .. && for d in debs/*.deb; do dpkg-deb -x "$d" root; done
```

Then **symlink them into Playwright's own `sys/lib`** rather than exporting
`LD_LIBRARY_PATH`, because `minibrowser-wpe/MiniBrowser` is a wrapper script that
*overwrites* `LD_LIBRARY_PATH` with its own two directories:

```bash
for t in ~/.cache/ms-playwright/webkit-*/minibrowser-{wpe,gtk}/sys/lib; do
  for so in "$PWD"/root/usr/lib/x86_64-linux-gnu/*.so*; do
    ln -sf "$so" "$t/$(basename "$so")"
  done
done
export PLAYWRIGHT_SKIP_VALIDATE_HOST_REQUIREMENTS=1
```

Two failures worth naming, because both look like "WebKit is broken" and neither is:
the wrapper's `LD_LIBRARY_PATH` overwrite above, and `libGLESv2.so.2`, whose absence
kills the web process **after** a successful `browserType.launch()` — so the error
surfaces as `browser.newPage: Target page, context or browser has been closed` with the
real cause (`Couldn't open libGLESv2.so.2`) only visible under `DEBUG=pw:browser`.

`MESA: error: ZINK: failed to choose pdev` remains on stderr for every run. It is
harmless — there is no GPU, the compositor falls back to software, and nothing in this
harness draws.
