# Synthetic `.xer` fixtures

Generated by [`tools/fixture-gen`](../../tools/fixture-gen/README.md). No client data
of any kind — every byte is synthesised, which is why these are committed while the
real fixtures never can be.

**They are the only test corpus CI will ever have.** Real `.xer` files are commercial
data and permanently gitignored, so a GitHub Actions run can never see one. Fork PRs
get no secrets either, so the corpus must need none.

## What is here

| Path | Kind | Job |
|---|---|---|
| `corpus/*.xer` | correctness | 29 files, ~20 activities each, one known landmine per file |
| `corpus/*.expected.json` | golden | what a parser must report for that file |
| `sparse-150.xer` | rendering | 150 activities — does the card look broken with barely any data |

Perf fixtures (20,000 activities, ~30 MB) are **not** here. They are reproducible from
a seed and land in `fixtures/generated/`, which is gitignored:

```bash
node tools/fixture-gen/generate.mjs --only perf-20k
```

## The golden files

`<fixture>.expected.json` is written from what the generator **intended to emit** —
never from parsing the result. A golden produced by our own parser would assert
nothing. A parser has to agree with the golden; the golden does not have to agree
with a parser.

Each one carries row counts per table, the assertions worth checking by name (status
mix, float nulls versus zeros, WBS depth, distinct `TASK.proj_id`, external
relationships), a **`driving_path` block** (below), a **`calendars` block** (below), an
`ingest` verdict where a fixture pins an ingest rule, and — for files small enough — a
full name-mapped dump of every activity. The two corrupt fixtures carry a **`readability` block** as well, measured off
the bytes rather than written from intent, because there is nothing in a corrupt file to
have intended: whether it starts with `ERMHDR`, whether its last record is `%E`, how many
`NUL` bytes it holds, and the verdict those imply.

Round-trip the whole corpus:

```bash
node tools/fixture-gen/measure.mjs --verify
```

## The `driving_path` block

Every golden carries one, because the generator walks the Longest Path over every
fixture it builds. It records **two** answers, and the difference between them is the
point:

| Field | What it is |
|---|---|
| `members` | The truth — the driving set the generator walked over its own logic network. `driving_path_flag` in the `.xer` is written from this and from nothing else, so it plays the same oracle role P6's own flag plays on a real file |
| `as_read_from_the_file` | What a tracer built to [014](../../docs/wayfinder/tickets/014-compute-critical-path.md) decision 4, **as amended by [028](../../docs/wayfinder/tickets/028-driving-test-relationship-types.md)**, can arrive at from these bytes alone: the demand each relationship *type* makes, scored against the successor timestamp it constrains, lag as elapsed hours, relationships absent from the file absent from the walk, predecessors outside the file unresolvable |
| `as_read_from_the_file.why` | Every activity where the two walks disagree — about which predecessor drives it, or about whether the walk starts there — and which of the five causes did it |
| `float_based_tracer` | What `total_float_hr_cnt <= 0` would mark instead. **This is not the Longest Path** and the corpus exists to say so |

The rule the second walk implements, in full:

| `pred_type` | demand | measured against |
|---|---|---|
| `PR_FS` | `pred.early_end_date + lag` | `succ.early_start_date` |
| `PR_SS` | `pred.early_start_date + lag` | `succ.early_start_date` |
| `PR_FF` | `pred.early_end_date + lag` | `succ.early_end_date` |
| `PR_SF` | `pred.early_start_date + lag` | `succ.early_end_date` |

Driving predecessors are the argmax of `demand − reference`, ties all kept — plus one
floor: a candidate demanding **strictly less** than its reference is dropped where the
two are the same kind of instant and the lag is zero (`PR_SS`, and `PR_FF` unless
exactly one row is a milestone). An empty pool means the activity is a chain tail. Every
quantity is a timestamp the file already carries, so nothing here decodes `clndr_data`;
on an all-FS successor the reference cancels and this **is** decision 4 as originally
written.

The `PR_FF` exception was written because a milestone wrote its finish *as* a start
instant, so the pair was not like-for-like.
[049](../../docs/wayfinder/tickets/049-generator-milestone-instant.md) removed that cause:
every row's finish is a finish now, and two finish instants order exactly as their working
hours do whether or not either row is zero-duration. The clause has still never executed —
25 `PR_FF` relationships here, exactly one with a milestone on a side, on an activity no
walk reaches — and removing it regenerates a byte-identical corpus, so it stands unchanged
and whether the *rule* should keep it belongs to
[028](../../docs/wayfinder/tickets/028-driving-test-relationship-types.md).

Score a tracer against `as_read_from_the_file`. The gap to `members` is the
approximation 014 knowingly accepted; across the corpus it measures **97.0% recall and
97.9% precision**, with **22 of the 28** files that have a readable walk reproduced
exactly on all six fields (membership, `state`, `branches`, `truncated`, `cycle_count`,
`path_continuous`). `enc-zeroed-file` is the twenty-ninth and has no readable walk at
all, because nothing in it parses. It is stated here rather than tuned away: **10
activities across six files** come out differently from the truth — 6 missed, four
marked in error, two of the six differing in structure rather than membership.

Five causes are named in `why`. Two are 014's own — the relationship is not in the file,
and the driving predecessor is outside it. Two more are the same physics twice: lag read
as elapsed hours across non-working time, and **mixed anchor kinds** — a finish instant
scored against a start instant on a *zero-lag* relationship, which is the residue 028
measured and refused to close, because the repair costs five other files.

**The fifth is the seed, and it is the one the walk itself cannot see.** Both walks span
remaining work back from the latest remaining finish (014 decision 3), but they read
*latest* on different scales: the truth in **working hours**, and the readable rule — which
has only the emitted timestamps — in **elapsed** time. Where two activities sharing one
working-hour finish write it as different wall-clock instants, one of them wins a seed race
the truth calls a tie; the readable walk then starts somewhere else entirely, every activity
both walks reach can still agree on its drivers, and a comparison of driving predecessor
sets has nothing to report — a non-empty `misses` beside `why: []`
([042](../../docs/wayfinder/tickets/042-seed-divergence-unnamed.md)).

**It has no corpus instance, because the thing writing one working moment as two instants
was this generator rather than P6.** Until
[049](../../docs/wayfinder/tickets/049-generator-milestone-instant.md) a zero-duration row's
finish went out as a **start** instant, so a finish milestone landed at the next morning's
`08:00` while the task it finished with sat at the previous afternoon's `16:00`, and the
reader ranked the milestone strictly later.
[044](../../docs/wayfinder/tickets/044-tracer-seed-tie-break.md) measured 28,695 real
milestone rows and found P6 doing the opposite in **96.4%** of them: a finish milestone is
written at its driver's `early_end_date`, and it is the *task's start* that a non-working gap
displaces (54.1% of 77,853 non-milestone rows). Every row now writes its finish at the end of
the working hour it occupies, zero-duration or not, so the emitted finish is strictly
increasing in the working hour and the two orderings coincide — 0 disagreements over 7,768
ordered pairs of remaining rows across the 29 programme fixtures.

There are three ties and every one of them ties in both walks: 23 files seed on one
activity and cannot diverge, and two have no seeds (100% complete). Two are a finish
milestone against the task it finishes with — `cal-flat-no-0x7f` seeds on `A001130`,
`A001170` and `A001190`, `multiproj-two-proj-id` on `A001170` and `A001190` — which is the
shape 044 measured on 47 of 47 real ties. The third arrived with
`cal-project-clndr-absent` and is the shape 044's measurement did not need: **two ordinary
positive-duration tasks finishing in the same working hour**, `A001160` and `A001190`, both
at `2026-08-18 16:00`. It ties for a duller reason than the milestone pair — two finishes
are the same kind of instant, so nothing has to be corrected for them to agree — and it is
worth having because it is the tie no milestone rule can explain away. `cal-flat-no-0x7f`
went from 4 missed activities to **100% recall at 100% precision**; the engineered branch
[022](../../docs/wayfinder/tickets/022-generator-longest-path-and-landmines.md) built into it
is untouched and still makes the file discriminate, it simply no longer costs a chain.

Both seed sets are stated against each other in `as_read_from_the_file.seed_agreement` —
`agree`, `truth`, `as_read`, `only_in_truth`, `only_in_read`, and `agree` is now **true on
every file** — and `measure.mjs --verify` **fails** any fixture whose `misses` or
`marks_in_error` is non-empty while `why` is empty. That invariant is still live on the four
causes that do have instances; what it no longer has is a fifth-cause instance to fail on, so
a generator reverting to four causes scores **29/29** and the cause is kept unexercised for
the same reason 028's milestone guard is — it is right, and it is the only thing that would
speak if a future emitter reopened the gap. What the invariant asserts is that a disagreement
is *explained*, not that every activity in a `misses` list carries its own entry: **4 of the
10** named activities appear in `why` by name, the other six being downstream of a divergence
named elsewhere on the same file.

Also in the block: `seeds`, `branches` (a driving path is a set, not a chain),
`truncated`, `cycle_count`, `path_continuous` and `open_chain_tails`.

## The `calendars` block

Every golden carries one, and it states what each `CALENDAR` row **means** rather than
how many there are:

| Field | What it is |
|---|---|
| `week` | All seven days, `works` and the shifts on each written `HH:MM-HH:MM`, plus that day's hours |
| `hours_per_working_day`, `working_days_per_week`, `hours_per_week` | The day length and the week the shift pattern actually describes |
| `exceptions` | In emission order, each with its decoded date, its `1899-12-30` day serial, whether it is **worked**, and the shifts if it is |
| `declared` | What the row *claims* — `day_hr_cnt` and `week_hr_cnt`. Recorded beside the meaning because neither can be trusted: on `cal-flat-no-0x7f` row 2 they read empty and 56 over a pattern working 40 |
| `serialisation` | How the meaning is written down — `layout`, `shift_attrs`, `pad_hours`, `view_node`, `has_0x7f`. None of it is meaning; all of it is a parser trap |
| `same_meaning_as` | This row decodes to the same calendar as that one, and `identical_bytes` says whether it does so in different bytes. `cal-flat-no-0x7f`'s entire reason for existing, and the one claim no per-row comparison against intent can make |

Written from the working-time model the generator packed into `clndr_data`, never from
reading the blob back. `measure.mjs --verify` decodes the emitted blob and compares —
implementing exactly what
[038](../../docs/wayfinder/tickets/038-calendar-shapes-and-0x7f.md) corrected, so each
wrong rule is a way to fail: read the shift attributes positionally and `cal-flat-no-0x7f`
comes back with a **minus eight-hour** day, match the time with `\d\d` and the same day
works **four hours** with its exception working day gone, give `0x7F` any meaning at all
and **27 of 29** fixtures stop decoding. Before
[043](../../docs/wayfinder/tickets/043-calendar-golden-block.md) the golden recorded
`calendar_count` and nothing else, and everything above lived in the `landmine` prose.

## What the calendars are for: `duration_working_days`

The block above states what a calendar means; this is the one stat that spends it. Every
golden carries `assertions.duration_working_days` and `assertions.calendars_in_use`, and
`measure.mjs --verify` decodes the emitted `clndr_data` and compares the whole object —
the day count, the calendar it was converted on, and the share of activities on that
calendar ([045](../../docs/wayfinder/tickets/045-duration-working-days-calendar.md), built
by [047](../../docs/wayfinder/tickets/047-report-duration-working-days.md)).

**The programme calendar is `PROJECT.clndr_id`**, taken from the row matching the
activities' `proj_id` — not `default_flag`, which marks the calendar new activities
inherit and on one real file names a calendar holding **0 of 1,746** of them. `days` is a
whole-day count over `time.start_date`..`time.finish_date` with **both ends in it**, which
is P6's own duration arithmetic and needs no day length; `span_calendar_days` beside it is
a **difference**, so on a calendar that works every day the working-day count is the span
**plus one**.

A value on **25 of 29**, `unavailable` on four, each for a different reason, and each
pinned by a file rather than argued:

| Fixture | State | Why |
|---|---|---|
| the other 25 | a value | 71.1–72.7% of the calendar-day window, because `PROJECT.clndr_id` names the five-day calendar. `wbs-flat` is **328** working days over a 459-day span |
| `missing-calendar` | `unavailable` | no `CALENDAR` table, so there is no shift pattern to convert on — 043's string, unchanged |
| `enc-zeroed-file` | `unavailable` | the same string, earned by a file with nothing in it at all |
| `cal-project-clndr-absent` | `unavailable` | `PROJECT.clndr_id 841` is not in the file's `CALENDAR` table. Two perfectly good calendars sit there and neither may be substituted |
| `multiproj-two-proj-id` | `unavailable` | activities span two projects, so there is no single programme calendar |

`activity_share_pct` is what stops the number claiming the whole programme: **50** on the
24 files that split ten and ten, **47.4** on `logic-external-driver` where one activity has
left the file, and **100** on `cal-default-unused`, which is the only file here shaped like
a real programme. The split is a shape **no real export produced** — distinct
`TASK.clndr_id` is 1 on 14 of 14 real files — and it stays because it is the only thing
exercising the share at all.

`calendars_in_use` counts distinct `TASK.clndr_id` and is the number the detail page's
Calendars tile wants: `cal-default-unused` declares **3** and uses **1**. It is counted off
`TASK`, so `missing-calendar` reports **2 in use against a `calendar_count` of 0** — the
rows still name calendars the file no longer carries, which is exactly what a table-level
deletion leaves behind.

The `error` state — the named calendar will not decode — is the only branch **no fixture
produces**, and `--verify` compares it on `state` alone because its reason is a decoder
diagnostic rather than an intent.

## Free float is per relationship type too

`free_float_hr_cnt` is the slack to the successor that gives least, measured in the
frame each relationship constrains and clamped at zero:

| `pred_type` | slack this successor leaves |
|---|---|
| `PR_FS` | `succ.ES − pred.EF − lag` |
| `PR_SS` | `succ.ES − pred.ES − lag` |
| `PR_FF` | `succ.EF − pred.EF − lag` |
| `PR_SF` | `succ.EF − pred.ES − lag` |

This is the same correction 028 made to the driving test, made one ticket later for the
same reason
([032](../../docs/wayfinder/tickets/032-generator-free-float-by-type.md)): the FS
formula was being applied to every type, and on **9 of the corpus's 529 float-carrying
rows** the answer was wrong — eight of them because the clamp turned an under-computed
slack into a spurious **zero**. 014 decision 4 reads `free_float_hr_cnt == 0` as
corroboration that a relationship is driving, so a wrong free float is a wrong answer to
the question this corpus exists to ask, and it is wrong in the direction that looks
right.

`measure.mjs --verify` now reads the column back by name and compares it to the golden.
Nothing did before 032 — the value was written into every golden and never read, which
is exactly why the defect survived two tickets working on the same file. A generator
that reverts to the FS formula now scores **24/29** rather than 29/29.

## A zero-duration row writes one instant, and it is a finish

A milestone occupies no working time, so the moment it records has two wall-clock names —
the end of the working hour before it and the start of the working hour after it — and on a
day boundary those are `2026-03-25 16:00` and `2026-03-26 08:00`. **P6 writes the first.**
Measured over 28,695 real milestone rows, 96.4% sit at gap 0 from their latest zero-lag
`PR_FS` predecessor's `early_end_date` against 0.8% one shift later, and it is the *task's
start* that a non-working gap displaces — 54.1% of 77,853 non-milestone rows
([044](../../docs/wayfinder/tickets/044-tracer-seed-tie-break.md) §4). This generator wrote
the second from [022](../../docs/wayfinder/tickets/022-generator-longest-path-and-landmines.md)
until [049](../../docs/wayfinder/tickets/049-generator-milestone-instant.md).

So a zero-duration row emits **one** instant for both of its dates, and
`early_start_date == early_end_date` — the reader-visible signal a finish milestone carries
in a real export, true on 35 of 35 non-completed zero-duration rows here and on no other row.
A row held by the project start rather than by a predecessor is written at the project start,
because there is no preceding working hour to end.

`measure.mjs --verify` reads all four dates back out of the emitted file by name and compares
them to the golden's activity dump. Nothing did before 049 — the values were written into
every golden and never read, which is why the rule stayed wrong through six tickets that
regenerated this corpus, and it is the fourth time this repo has found the same defect after
`driving_path_flag` (022), `free_float_hr_cnt` (032) and `float_path` (039). A generator
reverting to the old milestone instant now scores **6/29** rather than 29/29.

## The landmines

Each file isolates one, so a failure points at one cause. High bytes appear only in
the two encoding fixtures; a lone CR only in `text-multiline`; a `NUL` byte only in the
two unreadable fixtures, which are the only two files here that are damage rather than
programme. The eight `logic-*`
files are the tracer's landmines — seven added by
[022](../../docs/wayfinder/tickets/022-generator-longest-path-and-landmines.md) and
`logic-nonfs-drivers` by
[028](../../docs/wayfinder/tickets/028-driving-test-relationship-types.md); every
other file carries a `driving_path` block too, but none of them is *about* it.

| Fixture | What it exercises |
|---|---|
| `enc-mojibake-0x81` | `0x81` in `POBS`, and UTF-8 bytes sitting inside a CP1252 file. **Strict CP1252 decoding throws on this file** — as it does on the real Fixture B, which carries 31,485 of them |
| `enc-cp1252-currency` | `£ ¥ Ø` in `CURRTYPE` plus the CP1252 `0x80-0x9F` block (em dash, curly quotes) in activity names — the part of CP1252 that is not Latin-1 |
| `cal-clndr-data` | The indented `CA_Base` serialisation: `0x7F` runs, multi-shift days, exception **working** days, the `VIEW` node. All four confirmed against real exports by [021](../../docs/wayfinder/tickets/021-verify-fixtures-in-p6.md), so the golden asserts what they mean rather than that the parser survived them |
| `cal-flat-no-0x7f` | One calendar written **twice** — the indented `CA_Base` form and the flat `CA_Project` form real files carry beside it. The second row has no `0x7F` at all, writes shift attributes **finish first** (`f\|12:00\|s\|8:00`) and does not pad the hour (`s\|8:00`); both rows must decode to the same calendar. It also carries an empty `day_hr_cnt` and a `week_hr_cnt` contradicting its own pattern, because neither column can be trusted |
| `cal-default-unused` | The shape **both real programmes have and this corpus did not**: three calendars declared, all 20 activities on the one `PROJECT.clndr_id` names, and `default_flag = Y` on a seven-day calendar nothing uses. Read `default_flag` as the programme calendar and the span converts to 100% of itself instead of 71%. `calendars_in_use` is 1 against a `calendar_count` of 3, and its third row is a byte-identical project copy of its first — the corpus's only `same_meaning_as` pair with `identical_bytes: true` |
| `cal-project-clndr-absent` | `PROJECT.clndr_id` names calendar **841**, which is not in the file. `duration_working_days` must report `unavailable` naming the id, **not** fall back to `default_flag`, to the first `CALENDAR` row, or to the calendar most activities are on — all three are present and all three would produce a plausible number |
| `ver-60-fieldset` / `ver-83-fieldset` | The same programme in both `%F` field sets. Field **order** differs, so a positional parser reads one of them wrong silently. Name-mapped reads must produce identical stats from both |
| `missing-taskpred` | No `TASKPRED` table at all |
| `missing-calendar` | No `CALENDAR` table — no shift pattern, so working-day conversion has no basis. `day_hr_cnt` would not have supplied one either ([038](../../docs/wayfinder/tickets/038-calendar-shapes-and-0x7f.md)) |
| `wbs-flat` | `PROJWBS = 1`, Fixture B's real shape: `wbs_depth` is legitimately 1 |
| `progress-none` | 100% `TK_NotStart` — a pure baseline; a third of the stats are inapplicable |
| `progress-full` | Fully progressed, with actuals; completed activities carry **empty** float |
| `float-negative` | Negative float and null float in the same file |
| `multiproj-two-proj-id` | **Must reject**: activities under two distinct `TASK.proj_id` |
| `multiproj-baseline-rows` | **Must ingest**: three `PROJECT` rows, one owning `proj_id` |
| `text-multiline` | An embedded CRLF inside `task_name`, and a lone CR in another |
| `unknown-table-and-enum` | An undocumented table, `TT_LOE`/`TT_WBS`/`PR_SF`/`CS_MANDFIN` |
| `external-relationship` | `pred_proj_id` pointing outside the file — legitimate, not corruption |
| `enc-zeroed-file` | **Must reject as unreadable**: 397,781 bytes of pure `NUL`, the shape one real file in 139 actually has. Every count in its golden is zero, which is why no count can be the discriminator — a scan result of all zeros is indistinguishable from a very small programme |
| `enc-truncated-export` | **Must reject as unreadable**: a perfect header, whole tables, correct arity, and no `%E`. The file that says why "no `ERMHDR`" cannot be the rule. Pair it with `missing-taskpred`, which is the same shape and is legitimate — a sparse file ends with `%E` and a truncated one does not |
| `logic-driving-branch` | Three activities with **two** driving predecessors each — the Longest Path branches, so it is a set and not a chain |
| `logic-cycle` | A logic loop **on the driving chain**. `state: "error"`, `cycle_count: 1`, ingest still succeeds. The dates are deliberately incoherent — a cyclic file was never successfully scheduled |
| `logic-external-driver` | The chain's tail is an activity in another project, absent from the file. `truncated: true`, **not** a broken chain |
| `logic-complete-no-remaining` | 100% complete, so the walk has no remaining work. `state: "skip"` — which is neither error nor zero |
| `logic-lag-nonworking` | Multi-day FS lags on a five-day calendar: the case 014 decision 4 knowingly approximates. The golden **names** the activity where a date-reading tracer gets it wrong |
| `logic-nonfs-drivers` | `SS`, `FF` and `SF` relationships **on** the driving chain, not merely present in the file — including two `SF` predecessors that start *after* the activity they drive. No lags, no leads, so relationship type is the only possible cause of a disagreement. An `EF + lag` reader misses two activities, loses a branch and invents two; the per-type rule is exact, so this file fails any tracer that reverts. It is also where the FS free-float formula was most wrong — 5 of the 8 rows 032 corrected |
| `logic-no-longest-path` | P6 never ran Longest Path, so `driving_path_flag` is empty on every row — how most real exports arrive. 40 activities, behind its deadline: **19 carry float <= 0 and 4 are actually driving** |
| `logic-float-path` | `float_path` / `float_path_order` populated — 014's second oracle, and the corpus's strongest statement of 014's central claim. Path 1 is the **lowest-total-float chain**, 9 activities at −160 h; the 10 activities carrying `driving_path_flag = Y` are **path 3**, at zero float; the two sets **share nothing**. `float_path_order` is contiguous 1..n within every path, which is all this oracle validates. Measured against a real export by [021](../../docs/wayfinder/tickets/021-verify-fixtures-in-p6.md), rebuilt by [039](../../docs/wayfinder/tickets/039-float-path-semantics.md) |

## One fixture is speculative

`text-multiline` alone still carries `"speculative": true`. It encodes multi-line free
text, which the format permits and **no real file in hand exercises** — 139 real exports
contain not one embedded newline. What it asserts is that the parser survives and reports
what it saw, not that this is what P6 means by it. It is a defensive fixture against a
shape no real file has produced, which is worth keeping and worth labelling honestly.

Two fixtures left this section on 2026-08-08, both because
[021](../../docs/wayfinder/tickets/021-verify-fixtures-in-p6.md) settled them against real
exports, and in both cases the shapes were guessed correctly while the **rule** written
around them was wrong.

`cal-clndr-data` was speculative because the format research could not settle multi-shift
days, exception working days or the `VIEW` node by reading. All three are real, all three
were guessed correctly, and what was wrong was the *rule* — `0x7F` was charted as a
structural separator and is layout. Both are corrected
([038](../../docs/wayfinder/tickets/038-calendar-shapes-and-0x7f.md)), and the corpus now
carries `cal-flat-no-0x7f` to enforce the correction, because the old fixture parses
identically under the wrong rule and could never have failed it.

`logic-float-path` was half right. Order semantics held — `float_path_order` is contiguous
1..n along a path — and membership did not: path 1 is the lowest-total-float chain, not the
driving one, and in the real export it shared no member with `driving_path_flag = Y`. The
fixture was rebuilt around the real shape
([039](../../docs/wayfinder/tickets/039-float-path-semantics.md)). Oracle still documents
nothing about the column's contents; the corpus no longer relies on Oracle.

## Not verified against P6

These files have never been imported into P6. See the resolution of
[Get a large synthetic fixture for perf work](../../docs/wayfinder/tickets/012-large-synthetic-fixture.md)
for exactly what that does and does not cost.

They have, however, been read end to end by **MPXJ** — an independent third-party
implementation of the format — with zero failures across the 24 corpus files that existed
on 2026-08-08, `sparse-150` and all three perf fixtures, agreeing with the goldens exactly
on 20 of 24 and differing only where a fixture's landmine says it should. The fixtures
added by the corrections that followed — `cal-flat-no-0x7f`, `enc-zeroed-file`,
`enc-truncated-export`, `cal-default-unused` and `cal-project-clndr-absent` — were **not**
in that run, and neither, strictly, are the bytes that were: [049](../../docs/wayfinder/tickets/049-generator-milestone-instant.md) moved 370
date values on 41 rows across 23 files without changing one table, column, arity or field
width, so what that run proved about the *shape* of these files still holds and what it
proved about these exact bytes no longer has them. That is not the same claim as *P6 imports
them*, and [041](../../docs/wayfinder/tickets/041-p6-importer-acceptance.md) holds what is
left of the difference.
